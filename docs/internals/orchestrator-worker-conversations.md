# Orchestrator worker conversations

Worker controls belong to the originating assignment and conversation. COR-96 adds `sendWork`, `editWorkMessage`, `removeWorkMessage`, `reorderWorkMessages`, `answerWorkQuestion`, and `escalateWorkQuestion` to coordinator decisions. The existing `threads.control` capability controls writes; reading also requires `threads.read`, current project access and the conversation's shared history boundary.

The private Convex worker mailbox does not publish message bodies through company change feeds. `pending` means editable cloud intent. Environment acceptance checks the current revision and queue head atomically, then permanently freezes the message. `delivered` means the local orchestration command has been durably dispatched. It does not confirm that a provider processed it or finished the requested work. An uncertain accepted delivery keeps its command identity; recovery reads the local receipt before dispatching. A rejected receipt is not retried as new work.

Queued follow-ups stay in Cloud while a worker turn is active, retaining edit/remove/reorder controls. Answers and steering bypass these waiting follow-ups so a blocking question cannot deadlock the queue. An accepted message always retains priority until its receipt is recovered. Queue reordering uses the complete pending set; edits and removals require a matching revision. The mailbox currently bounds each assignment to 100 stored messages and 100 question records. Coordinator context is bounded separately.

The environment subscribes to the inbox and listens to question/run events. Streaming text does not trigger mailbox scans. New questions create one coordinator job; repeated reports, resolution and delivery acknowledgments do not create acknowledgment jobs. Allowance revision changes also invalidate the inbox subscription. Existing coordinator job scheduling and completion collection retain their existing scheduling behavior.

Questions retain both their Pathway thread and runtime request identity. The environment verifies inherited assignment origin and project ownership before reporting or answering. Only `user_input` requests with a resumable response capability are answerable. Approval requests are excluded. Answers sent through this channel carry agent provenance even when a provider needs a follow-up message to resume; text in a question or answer cannot authorize new capabilities or allowance.

Root worker steering uses the existing adapter policy: Codex, Claude and OpenCode support active steering; Cursor and ACP/Grok may use interrupt/restart steering. These are dispatch requests, not proof of provider receipt. Provider-native subagents have no independent send/stop endpoint here. Questions exposed through Pathway runtime requests can route to their original child conversation. Pathway-owned descendants preserve the assignment origin and its guards. Stop requests remain uncertain until durable terminal state is observed; offline accepted work is never redirected as though stopped.

Integration dependencies: COR-94 owns attachments and composer uploads; this mailbox is text-only and does not duplicate that implementation. COR-95 owns delegation selection and discovery; both changes touch coordinator context and the runtime prompt, requiring merge review. Worker controls live in separate web and SwiftUI components.

## Provider scope at the reviewed revision

These are repository adapter declarations, not certification of a live provider session. `CommandPolicy.decideSteeringExecution` prefers active steering and otherwise requires both interrupt and interrupt/restart support.

| Adapter     | Root worker steering                           | Native child IDs / close capability                      | COR-96 native child control                                                                                                 |
| ----------- | ---------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Codex       | Active steering; interrupt/restart fallback    | IDs exposed; adapter declares close support              | Answers can route to an exposed resumable child request. No independent mailbox send/stop action for a native child.        |
| Claude      | Active steering; no interrupt/restart fallback | IDs not exposed; no close support                        | No independently addressable native child control. Only questions actually projected as resumable Pathway requests qualify. |
| OpenCode    | Active steering; interrupt/restart fallback    | IDs exposed; no close support                            | Exposed IDs do not establish independent control. Same resumable-request gate applies.                                      |
| Cursor      | Interrupt/restart                              | IDs not exposed; no close support                        | No independently addressable native child control.                                                                          |
| Grok        | Inherits ACP interrupt/restart                 | Grok adds child IDs/lifecycle; inherits no close support | Lifecycle visibility does not establish independent control. Same resumable-request gate applies.                           |
| Generic ACP | Interrupt/restart                              | No subagent capability declared                          | No native child control.                                                                                                    |

Source: `apps/server/src/orchestration-v2/Adapters/*AdapterV2.ts` capability objects and `CommandPolicy.ts`. Codex's adapter-level close capability is not exposed as a COR-96 child stop action. `workerQuestions` only reports projected `user_input_request` items with matching runtime requests of kind `user_input` and a response capability other than `not_resumable`. Runtime delivery rechecks assignment origin and the original thread/request. A question's prose or a lifecycle item alone is insufficient. App-owned descendants are different from opaque provider-native subagents and must retain assignment origin and project authorization. The Codex child-question replay passes; no live native subagent run was launched for this review.
