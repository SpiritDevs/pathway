# Startup audit — September 2026

The largest measured client cost was loading every route before the app could render. Automatic route splitting halves the JavaScript initially requested by the production HTML. Backend changes remove repeated shell discovery, postpone provider probes until activation, select threads that may need recovery, and bound projection-rebuild memory.

## Measurements

Measurements used an Apple Silicon Mac, Node 25.9.0, this worktree's dependencies, and production Vite builds. Database reads used a consistent isolated snapshot containing 78 threads, 925 messages, 6,080 timeline items, and 16,930 retained events. No server was run against the live database.

| Measurement                                                          |               Before |                  After |
| -------------------------------------------------------------------- | -------------------: | ---------------------: |
| Main JavaScript bundle, minified                                     |              5.68 MB |                1.90 MB |
| All JavaScript referenced by initial HTML, including module preloads |              7.79 MB |                3.86 MB |
| Same initial files, individually gzip compressed                     |              2.33 MB |                1.20 MB |
| Initial JavaScript files                                             |                   21 |                     97 |
| Recovery history reads, median of three runs                         |  277 ms / 78 threads | 124 ms / 24 candidates |
| Full projection verification, first read                             |           716–726 ms |              Preserved |
| Full projection verification, warm reads                             |           289–300 ms |              Preserved |
| Projection rebuild's retained event batch                            | Entire event history |     At most 500 events |

The recovery timings exclude executing recovery effects. The old path also loaded a shell snapshot (26–31 ms), which the new path does not need. The benchmark alternates the order of the two history-read strategies; both run after verification has warmed the projection data.

Running both recovery strategies against identical isolated snapshots produced the same reconciliation counts and identical projection payloads after normalizing timestamps. Each cancelled one run and stopped one provider session.

An isolated backend with fresh state reached command readiness in 3.25 seconds before the changes. A subsequent run with initialized state and the changes took 2.95 seconds. These runs differ in migration/cache state and are diagnostic baselines, **not a controlled end-to-end speedup measurement**. They did not reproduce the reported 30–60 seconds on slower machines.

Route splitting increases request count while reducing download and parse volume. The production build was checked; packaged Electron rendering, high-latency connections, Windows, and WSL were not timed interactively. The figures above do not establish a desktop launch-time guarantee.

## Reproduction and support

Use an already migrated, consistent database snapshot, created with SQLite `VACUUM INTO` from a read-only source connection. Then run:

```sh
node apps/server/scripts/benchmark-startup.ts /absolute/path/to/snapshot.sqlite
```

The benchmark opens SQLite read-only and reports only counts and durations. It does not migrate, rebuild, reconcile, launch providers, or connect to cloud services. This measures the database portion, not the desktop shell or first rendered screen.

For client measurements, compare production builds from the two revisions with the same configuration. Sum the module script and JavaScript module-preload files in `dist/index.html`; comparing only `index-*.js` overstates the saving because shared dependencies move into separate chunks.

The server now logs `Server command ready` with `startupMs` measured from the backend process's start, including module loading. Startup phases lasting at least 250 ms are recorded at Info with `phase` and `durationMs`; Debug includes faster phases. Existing desktop/backend and tracing logs can distinguish shell setup, backend readiness, and window load. Backend `startupMs` does not include time spent starting Electron or resolving its shell environment.

## Verification and surface coverage

Focused tests cover bootstrap defaults and hydration handoff, WSL exclusion, initial provider refresh activation, recovery ordering, shared sessions, cross-thread provider relationships, archived recovery, settled-thread exclusion, idempotent recovery, pagination beyond 500 events, corrupt projection detection, and rollback on a late replay failure. Production web builds and scoped lint/typechecks cover the implementation.

The route change applies to web, hosted web, and Electron's shared renderer, including direct route navigation. It does not change menus, keybindings, authentication, or feature availability. Native mobile receives backend improvements without a client schema migration. The bootstrap addition is optional and confined to the desktop-to-server launch envelope, so older launchers retain the previous hydration path. Local, LAN, relay, and tunnel authorization remain intact.

The remaining unmeasured parts of the complaint are packaged cold launch on slower Windows/macOS machines, WSL cold boot, network/account waits, and time to a usable rendered screen. Full projection verification remains proportional to history size. These are explicit limits of this audit's runtime evidence.
